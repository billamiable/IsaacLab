Skill Proposal

Isaac Lab 机器人 Teleop Enablement Workflow 是否适合做成 Skill

结论：适合。它不应该被设计成“给一个机器人资产就全自动生成 teleop 环境”的黑盒，而应该设计成一个半结构化工程 workflow skill。 Skill 负责固定适配顺序、检查点、验证证据和常见坑；具体机器人、控制方式、任务环境仍由 agent 根据代码库做工程判断。

整理日期：2026-06-02。示例来自本轮 G1 Dex1 + Pico motion controller + Isaac Lab headless enable 过程。

1. 为什么这件事可以做成 Skill

这个工作流的输入和输出不像 PDF 转换或代码生成那样完全模块化，但它有稳定的阶段、稳定的判断问题和稳定的验收方式。 这正是 skill 适合承载的内容：不是替代工程判断，而是让 agent 每次做类似适配时按同一条证据链推进。

稳定输入

机器人资产、仿真描述、运动学描述、控制源、参考任务、期望的 teleop 语义。

稳定流程

资产确认、frame/joint 映射、action 设计、retargeter 接入、smoke test、视频验证、环境调整。

稳定输出

任务 cfg、retargeter、probe 脚本、报告、视频、启动命令、适配复盘文档。

Skill 的核心价值不是“写出某个固定文件”，而是持续追问五个问题： 控制源是什么？控制目标 frame 是什么？retargeter 做了什么坐标变换？Isaac Lab action space 最终收到什么？如何证明它真的按这个语义工作？

2. 建议的 Skill 边界

范围 应该包含 不应该承诺
机器人资产适配 指导 agent 区分 USD、URDF、meshes、kinematics URDF，并确认 joint/body/frame 名称。 不承诺自动修复所有 USD composition、URDF importer 或物理参数问题。
Teleop 接入 指导 agent 设计 controller raw data 到 Isaac Lab action 的 retarget path。 不假设所有机器人都用同一个 IK、同一个 end-effector frame 或同一个 gripper 表达。
Headless 验证 要求 smoke test、JSON/Markdown report、截图或视频，并把输出落到宿主机。 不把 headless 验证等同于真实 Pico 实机验证。
任务环境调整 指导 agent 调整 table、cube、camera、fixed base、success termination。 不承诺一次完成真实抓取或真实堆叠策略。

3. Skill 的输入和输出

输入

  • 仿真资产：USD 路径、依赖目录、mesh 目录。
  • 运动学资产：URDF 或 kinematics URDF 路径。
  • 控制源：Pico/OpenXR motion controller、hand tracking、keyboard 或 mock data。
  • 控制语义：wrist、palm、tool frame、gripper center、finger pads。
  • 参考任务：已有 humanoid 示例、Franka stack 示例、GR1T2/Galbot 任务。
  • 运行方式：docker/headless、是否需要 cameras、是否需要 Pinocchio/Pink IK。

输出

  • 新增或修改后的 task cfg / scene cfg / action cfg。
  • 新增或修改后的 teleop retargeter。
  • 资产关系和 name mapping 文档。
  • headless smoke test 脚本或现有 probe 的更新。
  • JSON/Markdown 报告、截图或 MP4 视频。
  • 实机 teleop / record_demos 启动命令。
  • 阶段性 commit。

4. 推荐阶段拆分

Phase A
资产和拓扑确认。 目标是确认 USD 能加载、URDF/meshes 能支持 IK、articulation joint/body/frame 名称清楚。 输出可以是 asset README、joint 列表、headless load screenshot。
Phase B
Isaac Lab 基础接入。 写或修改 ArticulationCfg、scene cfg、task registration，先让环境 reset/step 稳定。
Phase C
控制抽象和 retargeter。 明确 action space，例如 upper_body_ik(14) + left_gripper(1) + right_gripper(1)。 明确 raw controller pose 到 action 的语义和坐标变换。
Phase D
Headless smoke test。 用 mock controller raw data 验证 action shape、joint tracking、IK target、gripper open/close。 输出 JSON/Markdown report。
Phase E
视频验证。 用 headless camera 录视频，检查视觉上是不是目标部位在动。 这一步专门捕捉“代码数值看似对，但实际画面不对”的问题。
Phase F
任务和环境调整。 调 table/cube/camera/fixed base/success termination，让 teleop 场景接近实机可操作状态。

5. G1 Dex1 适配中的可复用例子

例子 1：USD 和 URDF 不是互相替代关系

本轮 G1 Dex1 资产不是简单把 URDF 直接转成 USD。实际做法是：以原 G1 USD 为基础，移除 Inspire hand； 再从完整 G1 + Dex1 URDF 转 USD 的结果中取出 Dex1 gripper 相关层，拼接到 no-hand G1 上。

文件类型 在 pipeline 里的作用 经验
USD Isaac Sim/Isaac Lab 里真实 spawn 的仿真资产。 可以通过 Gain Tuner 或 headless load 验证 articulation 是否合理。
URDF Pink/Pinocchio 运动学求解仍可能依赖它。 不要以为有 USD 后 URDF 就完全没用了；IK 仍要 frame/joint 拓扑。
meshes URDF 和 USD 可能都间接依赖 mesh 文件。 prune 资产时要先验证依赖，不能只看目录名判断是否 unused。

例子 2：4 个 prismatic joints 可以抽象成左右各 1D gripper

G1 Dex1 整体是 33 joints：G1 29DoF body 加 4 个 Dex1 prismatic joints。 虽然物理上每只手有两个 prismatic joints，但 teleop action 可以抽象成左右各 1 维 open/close。 

upper_body_ik:        14D = left wrist pose(7) + right wrist pose(7)
left_gripper_action:  1D = left Dex1 open/close
right_gripper_action: 1D = right Dex1 open/close
total action space:  16D

这个例子说明 skill 需要引导 agent 先确认“物理 DoF”和“控制抽象 DoF”的差异，再写 action term。

例子 3：Motion controller 位置不一定应该对应 wrist

一开始 mock Pico 和真实 Pico 的 controller xyz 被当成 wrist_yaw_link 目标。 实测发现这会导致用户手柄对齐的是腕部，而不是 Dex1 前面的并联爪。 后来修正为：controller xyz 表示 Dex1 gripper front-claw center，再由 retargeter 减掉 wrist 到爪心的偏移，得到 Pink IK 的 wrist target。 

controller_xyz = desired_gripper_center_xyz
wrist_target_xyz = controller_xyz - wrist_to_gripper_center_offset

right_wrist_to_gripper_center_offset ≈ [0.1505, -0.00006, -0.000008] m
left_wrist_to_gripper_center_offset  ≈ [0.1505, -0.00012, -0.000008] m

这个问题非常适合写进 skill：每次做 teleop 都必须明确 controller pose 对应哪个物理 frame。 如果不明确，代码可能能跑，视频也有动作，但真实操作会感觉“不跟手”。

例子 4：Headless smoke test 是为了提前抓低级错误

本轮用 mock Pico raw data 在 docker/headless 模式下验证了 retargeter 和 env action pipeline。 例如修正 gripper-center 映射后，smoke report 里能看到 controller 默认 x 约 0.355m， action 里的 wrist x 约 0.204m，正好减掉 Dex1 前爪约 15cm 的偏移。

验证项 证明什么
action shape = 16 IK action 和左右 gripper action 拼接正确。
trigger 使 gripper 从 open 到 close Pico trigger 到 Dex1 prismatic joints 的路径正常。
controller position 与 wrist action 存在 15cm offset 真实输入语义已经从 wrist 改成 gripper center。
MP4 视频 视觉上确认移动的是前爪，而不是腕部粘住 cube。

例子 5：任务环境调整也应该纳入 skill

G1 是人形机器人，不能照搬 Franka 任务里“桌子插在机械臂下方”的布局。 本轮先修正 table 与机器人碰撞的问题，再把任务四桌面默认高度从 TABLE_CENTER_Z=0.78 抬到 0.90。 结果是桌面顶面约 0.93m，cube 中心约 0.953m，更接近 G1 小臂横向工作高度。

这说明 skill 不能只关心 robot cfg 和 retargeter，也要包含 task scene calibration： robot fixed base、table pose、cube pose、camera view、success termination 都会影响 teleop 可用性。

6. 推荐 Skill 目录结构

第一版可以保持轻量，先把流程固化下来，不急着把所有 probe/render 脚本都变成通用工具。

asset_mapping.md USD/URDF/mesh/kinematics URDF 的职责边界和 prune/flatten 风险。

g1_dex1_case.md 本轮 G1 Dex1 作为 worked example，但不把它写死为唯一实现。

7. Skill 触发描述草案

Use this skill when adapting a robot asset in Isaac Lab or Isaac Sim for teleoperation,
especially when wiring USD/URDF assets, Pink IK, OpenXR/Pico motion controllers,
gripper retargeting, manager-based task scenes, headless smoke tests, or validation videos.

这个描述可以覆盖“已有机器人资产，想让它能被 Pico/teleop 控制”的场景，也能覆盖后续任务环境校准。

8. 给 Agent 的固定工作习惯

  1. 先问清或查清资产来源：最终 spawn 的 USD 是哪个，IK 用的 URDF 是哪个。
  2. 先列 joint/body/frame 名称，再写 action 和 retargeter。
  3. 每个控制输入都要声明语义：controller pose 对应 wrist、tool、palm 还是 gripper center。
  4. 先做最小切片：gripper only，再 scene，再 IK，再 teleop raw data。
  5. 每次改变 input mapping，都要跑 mock raw data smoke test。
  6. 每次改变视觉/任务环境，都要录视频或截图检查视角、桌面、cube、机器人姿态。
  7. 实机测试前输出明确启动命令；实机测试后把 observed issue 回写到流程。
推荐结论： 这应该被做成一个“半结构化工程 skill”。它的输入输出可以模块化到足够实用，但不能强行抽象成全自动转换器。 第一版最有价值的是固定 enable 顺序和验证标准，让以后适配新机器人时少走重复弯路。
